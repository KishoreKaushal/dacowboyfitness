What this builds

The site (dacowboyfitness.com) is a static Vue app on Firebase Hosting. This guide adds three things on top of it, staying on free tiers:

  • Sign in with Google — Firebase Authentication (no passwords to store).
  • Identity + entitlement store — Firestore: who the user is and which courses they've paid for.
  • Paid unlock — Razorpay (test/sandbox now) confirms a payment, your backend records the entitlement, and only then does the viewer get a Curriq student token to watch the videos.

It plugs into the player from the companion guide (docs/ai-docs/guides/…-curriq-integration-guide.html): everything here produces the authorized playback the player renders.

Prerequisite: the course + 5 videos must already be in Curriq (a one-time write-key script — companion guide Step 2 / ledger Work Package H). This guide is about access, not authoring.

The unlock model — read this first

Razorpay does not talk to Curriq, and Curriq has no “unlock this course” endpoint. Curriq (headless-lms) has no entitlement store — it gates AUTHENTICATED video purely on the presence of a valid student token (verified: access/policy.ts:12-13, gating is tenant-wide). So the unlock is realised on your side:
  1. Razorpay's webhook calls your backend when a payment is captured.
  2. Your backend writes an entitlement row to your Firestore (uid + courseId → paid).
  3. When the viewer opens the course, your token endpoint checks that entitlement and, only if paid, mints a Curriq student token.
  4. Curriq sees a valid token and streams the signed video. It never learns about the payment.

This is the correct headless split: money + identity + entitlement are yours; content + secure delivery are Curriq's. Wanting Razorpay to “tell Curriq” directly would require a per-course entitlement feature in the product — that's on the roadmap (see the ledger's “Next iterations”), not in this beta.

What's free on Firebase's Spark plan, and the one thing that isn't.

PieceFree?Limit / note

Cloud FirestoreFree (Spark)50,000 reads · 20,000 writes · 20,000 deletes per day; 1 GiB stored; 10 GiB egress/month; one free DB per project. A purchase = 1 write, opening a course = 1–2 reads → beta is nowhere near the cap.

Two ways to host the functions:
  • Simplest Firebase Blaze. Native firebase-admin (verifyIdToken, Firestore) and firebase-functions. Free at beta volume; requires a card. Recommended for speed.
  • Zero card Cloudflare Workers (or Vercel/Netlify functions), 100k req/day free. Keep Firebase for Auth + Firestore + Hosting; run the 3 functions here. More plumbing: you verify the Firebase ID token by hand (RS256 JWT vs Google's public keys) and read Firestore over its REST API. Same logic, no Admin SDK.
The code below uses Firebase Functions; the logic ports 1:1 to Workers.

Function 1 — createOrder (server-authoritative amount)

// functions/src/createOrder.ts
import { onRequest } from 'firebase-functions/v2/https';
import { initializeApp } from 'firebase-admin/app';
import { getAuth } from 'firebase-admin/auth';
import Razorpay from 'razorpay';
initializeApp();
const rzp = new Razorpay({ key_id: process.env.RZP_KEY_ID!, key_secret: process.env.RZP_KEY_SECRET! });

// price lives on the SERVER — never trust an amount from the browser
const PRICE: Record<string, { amount: number; currency: string }> = {
  'cowboy-way': { amount: 49900, currency: 'INR' },   // 499.00 INR, in paise
};

export const createOrder = onRequest({ cors: true }, async (req, res) => {
  const decoded = await getAuth().verifyIdToken(bearer(req));   // trust boundary #1
  const { courseId } = req.body;
  const price = PRICE[courseId];
  if (!price) { res.status(400).json({ error: 'unknown_course' }); return; }
  const order = await rzp.orders.create({
    amount: price.amount, currency: price.currency,
    receipt: `${decoded.uid}:${courseId}`,
    notes: { uid: decoded.uid, courseId },              // carried into the webhook
  });
  res.json({ orderId: order.id, keyId: process.env.RZP_KEY_ID, amount: order.amount, currency: order.currency });
});

function bearer(req: any): string {
  const h = String(req.headers.authorization ?? '');
  if (!h.startsWith('Bearer ')) throw new Error('missing token');
  return h.slice(7);
}

4Webhook → write the unlock

In Razorpay (Test Mode) → Settings → Webhooks: add your function URL, subscribe to payment.captured, and set a webhook secret.

// functions/src/razorpayWebhook.ts
import { onRequest } from 'firebase-functions/v2/https';
import { getFirestore } from 'firebase-admin/firestore';
import { createHmac } from 'node:crypto';

export const razorpayWebhook = onRequest(async (req, res) => {
  // trust boundary #2: verify the signature over the RAW body
  const signature = String(req.headers['x-razorpay-signature'] ?? '');
  const expected = createHmac('sha256', process.env.RZP_WEBHOOK_SECRET!)
    .update(req.rawBody)          // Firebase gives you the raw bytes
    .digest('hex');
  if (signature !== expected) { res.status(400).send('bad signature'); return; }

  const event = req.body;
  if (event.event === 'payment.captured') {
    const entity = event.payload.payment.entity;
    const { uid, courseId } = entity.notes ?? {};
    if (uid && courseId) {
      await getFirestore().doc(`entitlements/${uid}/courses/${courseId}`).set(
        { paid: true, orderId: entity.order_id, purchasedAt: Date.now() },
        { merge: true },
      );
    }
  }
  res.json({ ok: true });
});
This is the moment the course is “unlocked.” It writes exactly one Firestore document per purchase.

5Curriq student token (gated by entitlement)

Reuses the token endpoint from the Curriq guide, now backed by the Firestore entitlement instead of a stub.

This is Model A (per-student SSO token). For a simpler path that skips the SSO shared key entirely, see Model B below — it replaces this step and the browser reads in Step 6.

// functions/src/courseToken.ts
import { onRequest } from 'firebase-functions/v2/https';
import { getAuth } from 'firebase-admin/auth';
import { getFirestore } from 'firebase-admin/firestore';
import { mintIdpToken } from '@curriq/client/server';
import { CurriqClient } from '@curriq/client';

const TENANT = 'dacowboy';
const ISSUER = 'https://dacowboyfitness.com';           // must match the tenant's SsoConfig.issuer
const curriq = new CurriqClient(process.env.CURRIQ_API!);

export const courseToken = onRequest({ cors: true }, async (req, res) => {
  const decoded = await getAuth().verifyIdToken(bearer(req));      // who is this?
  const { courseId } = req.body;

  const ent = await getFirestore().doc(`entitlements/${decoded.uid}/courses/${courseId}`).get();
  if (!ent.exists || ent.data()?.paid !== true) { res.status(403).json({ error: 'not_entitled' }); return; }

  const idpToken = await mintIdpToken({
    sharedKey: process.env.CURRIQ_SSO_SHARED_KEY!,      // from provision-sso (server-only)
    subject: decoded.uid, issuer: ISSUER, audience: 'curriq', email: decoded.email,
  });
  const { studentToken, expiresIn } = await curriq.exchangeSsoToken(TENANT, idpToken);
  res.json({ studentToken, expiresIn });
});

Model B variant — read key (skip SSO) chosen for this build

Decision: for this beta — one paid course, identity already in Firebase — Model B is the path we build on: simpler, no SSO shared key, and the browser never holds a Curriq token. Model A (Steps 5–6 above) stays for reference, or for later if you want per-student identity inside Curriq.

Steps 5–6 use Model A (a per-student SSO token). Model B is simpler: your function holds a Curriq read key and reads Curriq directly after the Firestore entitlement check — no mintIdpToken, no exchangeSsoToken, and no SSO shared-key setup (you can skip Curriq Work Package G). The browser receives only the short-lived Mux token.

Trade-off: Curriq won't know which student watched (the read key is tenant-level). You already track the user in Firebase/Firestore, so for this beta that's usually fine. Choose Model A only if you want per-student identity inside Curriq (future progress/analytics).

Get a read key

Curriq dashboard → API tokens → create a read key (sk_live_…). Store it as CURRIQ_READ_KEY in your function's secrets — never in the browser.

One function replaces Step 5 + the browser reads of Step 6

// functions/src/course.ts
import { onRequest } from 'firebase-functions/v2/https';
import { getAuth } from 'firebase-admin/auth';
import { getFirestore } from 'firebase-admin/firestore';
import { CurriqClient } from '@curriq/client';
const curriq = new CurriqClient(process.env.CURRIQ_API!, process.env.CURRIQ_READ_KEY!);   // read key

export const course = onRequest({ cors: true }, async (req, res) => {
  const decoded = await getAuth().verifyIdToken(bearer(req));              // who
  const { courseId } = req.body;

  const ent = await getFirestore().doc(`entitlements/${decoded.uid}/courses/${courseId}`).get();
  if (!ent.exists || ent.data()?.paid !== true) { res.status(403).json({ error: 'not_entitled' }); return; }

  const outline = await curriq.getCourseOutline(courseId);                // one nested call
  const lessons: { title: string; playbackId: string; token: string }[] = [];
  for (const m of outline.modules)
    for (const l of m.lessons)
      for (const b of l.blocks)
        if (b.blockType === 'asset' && b.data.presentation === 'video') {
          const pb = await curriq.getVideoPlayback(b.data.assetId);       // Curriq-signed Mux token
          lessons.push({ title: l.title, playbackId: pb.playbackId, token: pb.token });
        }
  res.json({ lessons });                                                  // browser gets only Mux tokens
});

How students stay isolated & expiry is enforced

Two students, one course

Every request is keyed to the uid inside the verified Firebase ID token, and your function always reads entitlements/{that uid}/courses/{courseId}. Access follows a verified identity, not anything the browser can set:

  • Bob can't pose as Alice — the ID token is signed by Google; verifyIdToken rejects a forged one.
  • Alice's purchase doesn't help Bob — if entitlements/bob_uid/… is missing, the function returns 403; Alice's doc is never read for Bob.
  • Bob can't self-grant — Firestore rules let a user only read their own entitlement and let no client write it; only your backend (from the signature-verified webhook) writes it.
  • Bob can't skip the gate — the read key is server-only, so the browser can't call Curriq directly; the one door is /api/course, which checks his uid.
  • Multiple courses later — the entitlement is per courseId, so buying course X and asking for Y just 403s.

Come back 10 days later, auth expired → no play

Two short-lived tokens, neither durable, both re-issued only through your gate:

  1. The Mux playback token is short-TTL (max(MUX_PLAYBACK_TTL_SECONDS ≈ 900s, videoLength + 300)) and enforced at Mux's edge — one from 10 days ago is long dead.
  2. Getting a fresh one needs a fresh /api/course call → re-verify the Firebase token + re-check the entitlement. Stale login or lapsed access → 403 → no token → no video.

For time-limited access (a “30-day pass”), add expiresAt to the entitlement doc and reject when now > expiresAt before issuing. Nothing else changes.

Security checklist do not skip

RuleWhy
Verify the Firebase ID token server-side (verifyIdToken) on every functionThe browser could send any uid. Only a verified token proves identity.
Verify the Razorpay webhook signature over req.rawBodyAnyone can POST to your webhook URL. The signature proves it's really Razorpay.
Grant entitlement only from the webhook, never the client handlerThe client callback is skippable and spoofable.
Set the price on the server (PRICE map)Never trust an amount sent by the browser.
Keep secrets server-only: RZP_KEY_SECRET, RZP_WEBHOOK_SECRET, CURRIQ_SSO_SHARED_KEY, Curriq write keyThe browser only ever holds the Firebase config (public) and a short-lived studentToken.
Lock Firestore entitlements to backend-only writes (rules below)A signed-in user must not be able to write their own “paid: true”.
Use rzp_test_ keys + test webhook secret until you go liveSandbox first; swap to live keys only when verified.
On the Curriq server, keep MUX_SIGNING_KEY_PRIVATE in the environment onlyCurriq signs the Mux playback token with it (RS256, server-side) and never exposes it — the browser gets only the short-lived signed token. Don't commit it or bundle it (ledger F13).

Firestore security rules

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // A user may read only their own profile / entitlements.
    match /users/{uid} {
      allow read: if request.auth != null && request.auth.uid == uid;
      allow write: if false;                 // backend (Admin SDK) only
    }
    match /entitlements/{uid}/courses/{courseId} {
      allow read: if request.auth != null && request.auth.uid == uid;
      allow write: if false;                 // ONLY your functions grant access
    }
  }
}

The Admin SDK in your functions bypasses these rules, so your webhook can still write. allow write: if false blocks the browser from self-granting.
